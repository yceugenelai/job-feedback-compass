# 04 — フィードバックと志向分析

> 日本語訳です。エージェントが従う正本は `framework/rules/04_feedback_and_analysis.md`（英語）です。

本人が言う希望（stated preference）と実際の反応（revealed preference）はよく食い違う。フィードバックはこのフレームワークで最も価値のあるデータ。

## フィードバックの集め方

フィードバックの経路は2つ：
- **ファイルへの記入**：ユーザーが推薦ファイル（`workspace/agents/<agent-id>/recommendations/*.md`）の「あなたの感想」欄に書く。`<!-- status: pending -->` で記入済みのブロックが未処理。記録後、マーカーを `<!-- status: processed YYYY-MM-DD agent-id -->` に変更する。自分のものだけでなく**全エージェント**の推薦ファイルを確認する（読むのは可。そこで行う編集はこのマーカー変更のみ）。
- **会話**：ユーザーが求人について話す。

フィードバックが短い・曖昧なときは、1〜2 問だけ追加で質問する。例：
- 全体の評価：1〜5、または「応募したい／検討／見送り」
- **第一印象**（本当の理由であることが多い）
- 良かった点、気になった点
- 「X が違えば考えが変わりますか？」（決定的な要因を探る）

記録先：
1. カードの**ユーザーフィードバック**欄：**本人の言葉**、解釈、タグ。
2. `positions.tsv` の `status` と `rating`。
3. 企業そのものへの反応 → `companies.tsv`。

## フィードバックタグ

- 辞書：`framework/feedback_tags.md`（コミット対象。一般的な定義のみ、個人データなし）。
- **エージェントはタグを追加できる**：似たタグがないか確認し、日付と agent-id を付けて追記。
- タグの件数と該当例（個人データ）→ `workspace/shared/analysis/preference_model.md` の「タグ集計」。

## 分析

### preference_model.md（`workspace/shared/analysis/`、全エージェントで管理する生きた文書）

- **あなたへのまとめ**（ファイル冒頭）：ユーザー向けの短く平易な結論。**分析のたびに書き直す**。ユーザーが結果を見る場所。
- **発言と実際の反応**：本人の発言とフィードバックが示すこと。矛盾を列挙。
- **仮説**：例「年収よりリモートを重視している」。**根拠**（求人 id と引用）と**確度**（low / mid / high）付き。
- **推定される重み**。
- **要検証**：次の検索・会話で確かめること。
- **検索のヒント**：効果のあった手法・ソース（次に検索するエージェント向け）。

### 更新のタイミング

- **新しいフィードバックが 5 件以上**たまったとき、明確な矛盾が出たとき、ユーザーに頼まれたとき。
- 過程を `workspace/shared/analysis/log/YYYY-MM-DD_<agent-id>.md` に書き（テンプレート `framework/templates/shared/analysis_log.md`）、`preference_model.md` を更新。
- 他のエージェントの仮説を修正するときは、原文を残し「[日付 agent-id] 修正：…理由…」と追記。

### 簡易クロスレビュー（分析の一部。別プロセスは不要）

目的は**次の検索の改善**であり、エージェントの採点ではない。分析ログに小さな表を加える：

| 由来（found_by / 手法） | 推薦数 | 興味あり以上 | 所感 |
|---|---|---|---|

結論は `preference_model.md` の「検索のヒント」または「要検証」へ。

### ユーザーとの共有

- 発見はユーザーに**確認**する：「…のように見えますが、合っていますか？」。断定しない。
- ユーザーが同意した推論は `requirements_clarified.md` に昇格できる（出典 `inferred→confirmed`）。

## 原則

- 推論しすぎない：根拠 3 件以下は確度 low。
- エージェントごとに見解が違ってもよい。無理に統一するより「見解 A／見解 B」と並べる方がよい。
